# AI Image Studio — Updated Publishing Guide for the Corrected Android Build

**Applies to:** Checkpoint `52a5e39e`

**Purpose:** Replace the APK that crashes immediately after installation with a newly built release based on the corrected Expo configuration.

## What Was Fixed

The previous Android release was built from a project using **Expo SDK 54 with several Expo native modules from SDK 57**. Expo Doctor also detected that `expo-audio` required the direct `expo-asset` dependency. These native dependency mismatches can cause an installed standalone APK to crash before the first screen appears.

The corrected project now aligns the image picker, media library, sharing, and file-system packages with Expo SDK 54, adds `expo-asset`, registers the required Expo config plugins, and passes typecheck, lint, and reliability tests.

> **Important:** The old APK cannot be repaired after installation. You must generate and install a new APK from the corrected checkpoint.

## Part 1 — Prepare the Corrected Project

Open the project checkpoint for **Android startup-crash fix**. Confirm that the project version is `52a5e39e` or newer and that the project is not showing build errors. Do not use the old APK or AAB as the release artifact.

The project must keep the same package name if you intend to update an existing Play Console listing. Changing the package name creates a different Android application and prevents it from updating the existing installation.

Before building, verify that the app configuration contains the final app name **AI Image Studio**, the correct icon files, the production backend URL, and no `localhost`, `127.0.0.1`, preview-only, or development-only endpoints.

## Part 2 — Generate a Fresh APK for Device Testing

Use the project Management UI’s **Publish** panel. Choose Android, then choose **Build APK** for direct installation testing. Do not press the build button repeatedly while a build is processing. If the panel says that the build request is being processed, wait until the current build completes.

When the APK is available, download it from the generated build card. Verify that its version and package identity correspond to the corrected project. Keep the APK filename and build information in your release notes.

The APK is for direct device testing. For Google Play distribution, use the AAB generated by the same corrected project and release configuration.

## Part 3 — Remove the Old Crashing Installation

On the Android phone, uninstall the old **AI Image Studio** application before installing the corrected APK. This prevents stale native files, old cached configuration, and old application state from confusing the test.

If Android still reports a problem after uninstalling, restart the phone and confirm that the old package has disappeared from **Settings → Apps**. If the app was installed under a different package identity, remove that older package too.

Uninstalling may remove local app data. This is acceptable for this diagnostic installation because the old app is known to crash. For future production updates, test upgrades separately so that user data migration is verified.

## Part 4 — Install and Test the New APK

Enable installation from the source you used to download the APK only when Android asks for it. Install the new APK, open it immediately, and confirm that the Home screen appears without an Android System crash notification.

Run this exact smoke test:

| Test | Expected result |
|---|---|
| Cold launch | Home screen opens without closing |
| Background and return | App returns without a blank screen or duplicate UI |
| Prompt entry | Keyboard opens and text can be entered normally |
| Empty Generate tap | App explains that a prompt or reference image is needed |
| Text generation | Progress state appears, then a result appears |
| Gallery picker | Picker opens when Add reference image is tapped |
| Picker cancellation | App returns normally without a crash |
| Camera denial | App shows a clear permission message and remains usable |
| Settings | Settings expand and collapse without layout failure |
| Creations | Gallery opens and cards display correctly |
| Saved | Save and unsave state updates correctly |
| Full-screen viewer | Viewer opens and closes correctly |
| Download | Image is saved to the device gallery when permission is granted |
| Share | Android share sheet opens when sharing is available |
| Profile | Profile opens and edits can be saved |
| Offline launch | App remains open and shows a usable local interface |
| Offline network action | User receives a readable connection message rather than a hang |

Test the APK on at least two different Android devices or emulators, preferably one modern device and one lower-memory device. Also test at least one small portrait screen and one large screen.

## Part 5 — If the New APK Still Crashes

Do not reinstall the old APK. Collect the following information:

1. Phone manufacturer and model.
2. Android version and security patch level.
3. Whether the app crashes immediately or after tapping a feature.
4. Whether the app was uninstalled before installing the new APK.
5. The exact APK filename and build version.
6. A screenshot of the Android crash notification.
7. The first visible action before the crash.

If possible, capture Android crash logs through Android Studio Logcat or provide the device’s crash details. A crash that remains after dependency alignment may be caused by a device-specific native module, a release-only configuration, an incompatible ABI, or an error in a platform plugin. It cannot be diagnosed reliably from the Android System notification alone.

## Part 6 — Prepare the Google Play AAB

After the corrected APK passes physical-device testing, use the Publish panel to create the corrected **AAB**. Do not upload the old AAB. The AAB must use the same package name and compatible signing identity as the existing Play listing.

For an update, increase the version code. Never reuse the version code from the crashing release. Use a clear version name such as `1.0.1` or `1.0.2`, depending on the current store version.

The AAB is the preferred Google Play upload format because Google Play generates optimized APKs for individual device configurations.[1]

## Part 7 — Internal Testing

Upload the corrected AAB to an Internal testing track first. Add your own Google account and trusted testers. Install the Play-delivered build—not the sideloaded APK—and repeat the smoke test. This catches signing, Play delivery, device configuration, and release-only issues.

Compare three installations separately:

| Installation | Purpose |
|---|---|
| Fresh sideloaded APK | Confirms direct APK startup and native packaging |
| Fresh Play internal-test install | Confirms Play signing and delivery |
| Update over prior test build | Confirms version code, signing, and data migration |

## Part 8 — Closed Testing and Production Access

If the Play Console account is a personal account created after 13 November 2023, Google requires a closed test with at least **12 opted-in testers continuously for at least 14 days** before production access can be requested.[2]

Tell testers to install from the Play testing link, remain opted in for the complete period, and test the actual features. Maintain a written record of bugs, fixes, retests, device models, and tester feedback. Apply the fixes before requesting production access.

## Part 9 — Store and Privacy Requirements

Before public release, complete the store listing, content rating, target-audience form, app-access instructions, privacy policy, and Data safety form. Google requires Data safety information for apps published on Google Play, including apps distributed through closed or open testing; the declarations must match data collected by the app, backend, and third-party SDKs.[3]

For AI Image Studio, review at minimum:

| Data or capability | Release question |
|---|---|
| Google account | Is the name, email, or profile photo collected and why? |
| Prompts | Are prompts stored, sent to an AI provider, or used for training? |
| Reference images | Where are uploads stored and how are they deleted? |
| Generated images | Are images private by default and user-deletable? |
| Camera | Is permission requested only when the user chooses camera? |
| Gallery | Is permission handled correctly when the user chooses or downloads an image? |
| Analytics/crash tools | What third-party SDKs receive device or diagnostic data? |

Do not publish until the live backend, privacy policy, and Data safety answers agree with each other.

## Part 10 — Production Release

After internal and closed testing are successful, create the production release in Google Play Console. Upload the corrected AAB, review the release notes, choose countries and availability, and submit for review. Use a staged rollout where available so that crashes or backend failures affect a limited group first.

Monitor startup crashes, ANRs, login failures, generation failures, provider timeouts, image-storage errors, download failures, and support requests. If a serious problem appears, pause the rollout and release a focused fix with a higher version code.

## Recommended Release Notes

> **AI Image Studio 1.0.1**
>
> This release improves Android startup reliability, updates native dependencies for compatibility, improves connection failure handling, and adds safer image fallback behavior. We also refined the image creation, gallery, saved images, and profile experience.

## Final Go/No-Go Checklist

Do not distribute the corrected build publicly until all of the following are true:

- The new APK opens after uninstalling the old APK.
- The new APK opens on at least two Android devices.
- The Play Internal testing build opens successfully.
- The AAB has a higher version code than the previous store release.
- The package name has not changed.
- The signing identity is compatible with the existing Play listing.
- No release configuration points to localhost or a preview-only server.
- Camera and gallery permission-denial paths work.
- Download and share work on physical devices.
- Offline and timeout states are understandable.
- The privacy policy is public and accurate.
- The Data safety form matches the real backend and SDK behavior.
- Login and reviewer access work if authentication is enabled.
- AI generation, quotas, provider failures, and private storage are tested.
- A support email and crash-reporting process are ready.
